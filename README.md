# Teiko Immune Cell Analysis

This repository contains my solution for the Teiko technical assessment. The project loads the provided immune cell count data into SQLite, calculates relative cell frequencies, compares responders and nonresponders, runs the requested subset queries, and presents the results in a Streamlit dashboard.

## Dataset

The input file is `cell-count.csv`. It contains 10,500 samples from 3,500 unique subjects. Initial inspection showed that every subject has exactly three samples, corresponding to day 0, day 7, and day 14.

Five immune cell populations are measured: B cells, CD8 T cells, CD4 T cells, NK cells, and monocytes.

I also checked which fields were consistent within each subject. Project, condition, age, sex, treatment, response, and sample type remain constant for each subject in the provided dataset. This helped determine how to structure the database.

## Code Structure

The project is split into small scripts so each stage of the analysis can be run and checked independently.

- `inspect_data.py` explores the original CSV and checks the structure of subjects, samples, missing values, and duplicates.
- `schema.sql` defines the relational SQLite schema.
- `load_data.py` creates the database and loads subjects, samples, and cell counts from the CSV.
- `check_db.py` performs basic checks on the loaded database, including row counts and sample-level joins.
- `calculate_frequencies.py` calculates the relative frequency of each immune cell population for every sample and writes `cell_frequencies.csv`.
- `run_statistics.py` performs the responder versus nonresponder analysis and generates `statistical_results.csv` and `response_boxplots.png`.
- `query_subsets.py` runs the requested Part 4 database queries.
- `dashboard.py` provides an interactive Streamlit view of the Part 2–4 results.

I kept these stages separate instead of putting the entire workflow into one Python file because it makes each step easier to test, debug, and reuse. The Makefile connects the individual stages so the complete analysis can still be reproduced with a single `make pipeline` command.

## Running the Project

From the repository root:

```bash

make dashboard
```

`make setup` installs the dependencies. `make pipeline` recreates the database and executes the complete Part 1–4 analysis sequentially without manual intervention. `make dashboard` starts the Streamlit dashboard.

The database can also be created independently with:

```bash

```

## Part 1: Data Management

The SQLite database contains three tables: `subjects`, `samples`, and `cell_counts`.

```text
subjects
   |
   | one-to-many
   v
samples
   |
   | one-to-many
   v
cell_counts
```

### subjects

Stores subject-level metadata:

- `subject_id`
- `project`
- `condition`
- `age`
- `sex`
- `treatment`
- `response`

`subject_id` is the primary key.

### samples

Stores sample-level information:

- `sample_id`
- `subject_id`
- `sample_type`
- `time_from_treatment_start`

`sample_id` is the primary key and `subject_id` connects each sample to its subject.

Although `sample_type` is constant within each subject in this dataset, I kept it at the sample level because it describes the biological sample and could vary between samples in another dataset.

### cell_counts

Stores:

- `sample_id`
- `population`
- `count`

The combination of `sample_id` and `population` is the primary key.

The original CSV has five separate cell-count columns. During loading, these are converted into long format so each sample has five rows in `cell_counts`. With 10,500 samples and five populations, the table contains 52,500 records.

I chose this structure because subjects, samples, and cell measurements represent different levels of the data. It avoids unnecessarily repeating subject metadata and also makes the measurement table easier to extend. If another cell population is added later, it can be stored as another population value rather than requiring a new database column.

This structure can support hundreds of projects and thousands of samples without changing the schema. New subjects and samples are added as rows rather than requiring structural changes. The long-format `cell_counts` table also supports additional cell populations without adding new columns. Keeping subject, sample, and measurement data separate makes it easier to perform different types of analysis, such as comparisons by project, treatment, response, sample type, time point, or cell population. For larger datasets, indexes could also be added to commonly filtered fields to improve query performance.

## Part 2: Relative Cell Frequencies

For each sample, `total_count` is the sum of the five immune cell counts. The relative frequency is calculated as:

```text
percentage = count / total_count * 100
```

The resulting table contains:

```text
sample
total_count
population
count
percentage
```

The output is saved as `cell_frequencies.csv` and contains 52,500 rows.

The SQL uses:

```sql
SUM(count) OVER (PARTITION BY sample_id)
```

to calculate the total for each sample without collapsing the individual population rows. As a validation check, I confirmed that the five percentages for each sample sum to approximately 100%.

## Part 3: Responder vs Nonresponder Analysis

The comparison was restricted to melanoma patients treated with `miraclib` with PBMC samples.

This subset contains 656 subjects: 331 responders and 325 nonresponders.

Each subject has three repeated measurements. Since samples from the same subject are not independent observations, I averaged the relative frequency of each population within each subject before comparing responders and nonresponders.

A two-sided Mann-Whitney U test was used for each of the five immune cell populations. I used a non-parametric comparison rather than assuming the relative-frequency distributions were normally distributed.

Since five comparisons were performed, I applied Benjamini-Hochberg false discovery rate correction.

No population remained statistically significant after correction at an FDR threshold of 0.05.

CD4 T cells had the smallest raw p-value:

```text
Responder median:       30.21%
Nonresponder median:    29.82%
Mann-Whitney U:         59,855
Raw p-value:            0.0124
Adjusted p-value:       0.0621
```

The raw p-value was below 0.05, but the adjusted p-value was above 0.05, so the result was not considered statistically significant after correction.

The full results are saved in `statistical_results.csv`, and the distributions are shown in `response_boxplots.png`.
